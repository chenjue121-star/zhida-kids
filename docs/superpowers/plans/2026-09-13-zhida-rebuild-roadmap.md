# 智搭重构技术架构与分阶段规划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将已确认的首版需求拆为四个可独立验收的实施阶段，建立家庭共享、低负担录入和可解释推荐的数据基础。

**Architecture:** 推荐采用模块化单体后端，API 与持久任务 worker 分进程运行，共用领域服务与 MySQL。微信小程序按业务模块重建；推荐建议与家庭已选方案分开保存。本文是技术提案和实施总纲，各阶段需在执行前展开对应的逐任务计划，不冒充可直接执行的完整代码清单。

**Tech Stack:** 建议沿用微信原生小程序、Python/FastAPI、SQLAlchemy/MySQL、COS；新增 Alembic 管理新结构版本。识别、推荐和天气用适配器隔离供应商；首版不引入微服务或额外消息基础设施。

---

## 1. 依据与现状

产品基准：`docs/superpowers/specs/2026-09-13-zhida-rebuild-product-design.md`，已由用户确认。

本次实际核对的代码：

| 现有文件 | 当前行为 | 新需求影响 |
| --- | --- | --- |
| `backend/app/models.py` | Child 属于 user；Clothing 属于一个 child；height 必填 | 改为家庭归属、单件实物与孩子适配分离；身体信息允许未知 |
| `backend/app/routers/diaries.py` | POST 查同孩子同日期并覆盖；按日返回单对象 | 日历读取已选方案列表；创建与修改明确分离 |
| `backend/app/services/outfits/cache.py` | 使用 date.today，签名缺少偏好与身体信息 | 明确 target_date、家庭时区、偏好主体和输入版本 |
| `backend/app/routers/outfits.py` | 一次请求内调用模型和兜底；按个人授权 | 家庭授权、可恢复任务、独立建议与选定事务 |
| `backend/app/main.py` | 启动时 create_all | 新版通过显式迁移部署，不靠 create_all 演进旧表 |
| `miniprogram/app.js` | 当前孩子使用数组索引；全局单一天气 | 使用稳定 child_id；按孩子、日期、偏好主体保存上下文 |

现有识别、图片存储和推荐已拆出服务目录。可参考与测试复用其中的解析、枚举、COS 适配、审美包和评估样本，不直接把个人归属和旧日记语义迁入新版。

## 2. 架构选择

| 方案 | 好处 | 代价 | 建议 |
| --- | --- | --- | --- |
| 新版模块化单体，旧版可并行验证 | 家庭与方案语义清晰，发布风险可控制 | 临时维护两个版本 | 推荐 |
| 在现有接口原地修改 | 初期目录和部署变化少 | 旧前端、单用户权限和日记语义容易互相牵制 | 不作为默认 |
| 拆成多服务 | 各服务可独立部署 | 对当前规模增加通信、部署与事务成本 | 目前不采用 |

提案：执行时在隔离分支构建 `backend/app/v2/` 和 `miniprogram-v2/`，新 API 统一 `/v2`。先使用独立测试数据库，不触碰现有业务表。旧版保留到新版验收；共享部署还是独立部署在上线计划中依据实际环境决定。

该结构只是代码边界，不意味着每个模块需要单独服务。相同能力只保留一个受测试的实现，复用必须显式注入，不能导入旧路由触发应用初始化。

## 3. 模块与文件责任

以下是拟新增路径，不表示文件已经存在：

```text
backend/app/v2/
  main.py                        # 应用组装、健康与就绪检查
  core/config.py                 # 显式加载配置，供应商缺失按能力降级
  core/database.py               # 会话与事务边界
  core/errors.py                 # code/message/request_id 统一错误
  families/{models,schemas,router,service,access}.py
  children/{models,schemas,router,service}.py
  wardrobe/{models,schemas,router,service}.py
  media/{models,router,service}.py
  recognition/{models,router,service,normalize}.py
  recommendations/{models,router,service,signature,validation}.py
  plans/{models,router,service,reservations}.py
  preferences/{models,router,service,learning}.py
  jobs/{models,worker,repository}.py
  integrations/{ark,gptsapi,cos,weather}.py
backend/migrations-v2/           # 仅管理新版数据库
backend/tests/v2/                # 权限、事务、恢复及推荐契约
miniprogram-v2/
  app.{js,json,wxss}
  pages/{outfits,wardrobe,calendar,profile}/
  packages/family/               # 家庭与邀请
  packages/children/             # 档案与偏好
  packages/intake/               # 拍摄、待确认、恢复
  services/{api,session,media,jobs}.js
  stores/{context,drafts}.js
  components/                   # 可复用的真实单品、选择器等
```

router 负责 HTTP 和权限入口；service 负责用例、事务与领域规则；integration 负责供应商传输和响应解析。跨模块通过服务调用，不在页面或供应商适配器内隐式写业务状态。

## 4. 数据模型

| 实体 | 关键内容与约束 |
| --- | --- |
| User | 微信身份；不作为孩子和衣物的唯一所有者 |
| Family / Membership | 家庭时区地点；用户角色和成员状态；family_id/user_id 唯一 |
| Invitation | 哈希保存的邀请凭据、期限、角色、使用状态；接受事务防重复 |
| Child / Measurement | 家庭归属、生日、档案版本；可空身体信息及测量日期 |
| Garment | 一件真实实物，家庭归属、图片资产、类别、厚薄、可用状态、版本 |
| ChildGarment | 哪些孩子可以使用该实物及各自合身状态；转交结束原适配并建立新适配 |
| MediaAsset | 家庭范围 hash、对象 key、大小与类型；URL 为派生访问地址 |
| IntakeBatch / IntakeItem | 上传与识别状态、候选、确认归属、错误与恢复信息 |
| Job | 幂等键、状态、重试次数、租约、结果与取消信息 |
| PreferenceProfile / Feedback | 孩子、家庭／成员主体、显式标签、推断权重与版本；独立原始事件 |
| Recommendation | 输入签名、候选、来源、规则版本、建议结果；可重新计算 |
| OutfitPlan / PlanItem | 日期、主搭配／备用、选择人、版本、单品快照；是共享已选方案 |
| Reservation | 家庭、日期、实物、关联方案，用于跨孩子占用提示 |

数据库唯一约束承担幂等兜底，不能只靠“先查询再插入”。方案项保存单品快照，衣服编辑或归档不改写历史；图片删除遵守方案快照引用关系。

## 5. 核心协议与事务

### 5.1 家庭访问

每次请求同时验证登录用户、有效成员身份、角色和目标对象的 family_id；客户端传 family_id 不代表获得权限。仅查看角色禁止创建识别任务、上传及任何修改。移除成员后下一次请求立即失去权限。

邀请建议默认 7 天有效、一次接受后失效；创建者可撤销。最后一位管理员不能直接退出或被降级。退出仅移除成员关系，不删除家庭数据。参数在配置中明确，执行前写入家庭模块规格。

### 5.2 上传与识别

客户端先按家庭查询文件 digest 缓存，服务端重新计算 hash，并以家庭内唯一约束防并发重复。不同图片的同款相似度只能提示；上传去重不等于实物去重。

COS 存对象 key，不将短期签名 URL 当身份。新设计建议私有桶按需签名给小程序及模型访问，签名有效期覆盖任务等待与供应商读取时间；访问失败可刷新签名重试。历史公有读配置不在规划阶段修改。

识别请求提交后返回 202 和 job_id；worker 完成后保存候选，前端查询结果。只在确认接口创建 Garment；确认使用稳定幂等键，防重复点击生成两件。每个候选独立成功／失败，批次不因一项失败全部回滚。

任务租约超时后可重领、重启可恢复；供应商 429/临时网络/5xx 有限退避，参数或鉴权错误不盲重试。外部请求已经提交但响应丢失时标记结果不确定，避免无提示重复计费。

### 5.3 推荐与方案

```text
输入：family_id、child_id、target_date、scene、preference_mode、locked_ids、excluded_ids
服务端补全：目标日天气、档案版本、偏好主体/版本、有效衣橱、占用版本、规则版本
处理：授权 → 归一化签名 → 建议缓存 → 筛选/评分 → 模型辅助 → 强校验 → 规则兜底
输出：recommendation_id、items、reason、warnings、source、cached、input_version
选定：recommendation_id + 已调整单品 + target_date + idempotency_key
```

缓存日期用家庭时区解释的显式 target_date，不使用服务器 date.today。气象签名包括地点、日期、天气字段及已确定的归一化精度；仅采集时间变化不应使相同天气反复重算。天气未知必须进入签名与告知状态。

相同上下文的“换一套”用独立尝试幂等键并排除当前组合，成功后成为该上下文最新建议；固定或排除条件不污染无约束缓存。建议命中后仍校验权限及单品可用性。

选定方案在短事务内重新校验单品、占用与版本，创建方案/快照/反馈事件。模型调用不占用数据库事务锁。

PATCH 方案必须提交 expected_version；数据库条件更新不匹配返回 409，前端展示最新内容并允许重新调整。新增方案使用 POST，新 id；重复提交相同幂等键返回同一 id。

占用建议按目标日期保守提示，主搭配和备用均可占用；不同孩子冲突返回 409。确需分时共用时由用户显式确认并记录覆盖原因，不静默允许，也不自动阻断同孩子当天延续穿着。

### 5.4 偏好学习

显式标签、系统推断分开存。所有反馈保留操作者、孩子、推荐依据、原因、事件幂等键。初始建议：显式设置优先；选定为弱正向；至少三个不同方案上的同向行为才展示推断标签。临时不可用、未补记不进入审美评分。

推断只调整审美排序，不改变舒适和合身过滤。删除推断标签后记录其证据截止位置，不立即用同一批旧事件重建。权重公式、封顶和衰减用可版本化配置与固定样本评估后确定，不把任意数值宣称为已验证效果。

## 6. 前端状态与异常

- 当前上下文使用 family_id/child_id/target_date/preference_subject，不使用数组索引。
- 服务端是家庭数据与方案的来源；本地缓存按账号和家庭分区，退出清除当前身份缓存。
- 进入页面、切回前台时轻量刷新版本；第一页仍可展示旧方案但标注过期，权限失败清除对应家庭缓存。
- 切换上下文后，旧请求即使较晚返回也不能覆盖新孩子的页面。
- 上传尚未成功的临时文件需要持久化保存；保存失败明确提示，不能承诺退出后可恢复。
- 推荐加载保留原方案；批次局部失败允许继续；前端不另建与后端不同的推荐算法。

## 7. 分阶段实施路线

每阶段在执行前形成单独的完整文件级计划和测试任务。以下是依赖和验收边界，不是开发工时承诺。

### A. 家庭和孩子：先建立正确归属

- [ ] 新版独立数据库与迁移、应用入口、错误契约、配置加载。
- [ ] 微信身份登录适配，家庭/成员授权矩阵、邀请接受与退出。
- [ ] 孩子可空档案、测量记录、偏好依据及稳定上下文切换。
- [ ] 小程序完成登录 → 创建/加入家庭 → 建档 → 查看孩子列表。
- [ ] 验收：两个账号共享、第三账号拒绝访问、仅查看不可写、最后管理员约束、无照片建档、切换账号不串数据。

### B. 衣橱和集中录入：得到可推荐的真实衣物

- [ ] COS 资产、服务端 hash、批次与持久任务、识别适配与多件候选。
- [ ] 确认入库、默认合身可穿、状态、转交/共用、原图与单品对应。
- [ ] 小程序连续拍照、多选、集中确认、中断恢复、网格详情。
- [ ] 验收：重启恢复、并发同图去重、重复确认不重建、同款多件不误合并、权限移除后任务结果不可读取。

### C. 每日推荐与选定：主流程闭环

- [ ] 天气今天/明天适配、审美库加载、候选过滤评分、模型强校验与兜底。
- [ ] 签名与缓存、强制换套、固定单品、备用、占用及选定事务。
- [ ] 小程序首页真实衣物、独立孩子上下文、选定/修改/新增及家庭刷新。
- [ ] 验收：跨日时区、不同偏好缓存隔离、锁定不丢失、共用冲突、版本冲突、重复选定、已选不被天气覆盖、供应商失败仍可继续。

### D. 个性化、日历与上线验证

- [x] 反馈事件、标签查看修改删除、推断证据与版本、临时原因隔离。
- [x] 日历从方案读取同日多条、修改撤销、复用前重校验；不伪造穿着事实。
- [x] 家庭权限全流程与固定 0–6 岁测试衣橱、多宝、天气异常回归。
- [ ] 小程序开发者工具和真机验证；模型真实烟测用明确授权测试素材。开发者工具日历/偏好联通与原生空态、授权两张衣物图片烟测已通过；双真机与有内容的原生完整流程待验收。
- [ ] 数据迁移演练、备份、发布切换和回退演练后才切换实际使用入口。合成旧数据演练、SQLite切换/回退模拟、真实本地MySQL与私有媒体备份恢复已通过；生产环境发布/回退和实际入口切换待执行。详见 `docs/runbooks/zhida-phase-d-acceptance.md`。

## 8. 旧数据与供应商处理

旧版数据库、图片及未提交改动不删除。迁移默认先离线试跑到新版测试库，以来源 id 唯一映射保证重复试跑不复制数据；用户是否需要迁移实际历史在执行迁移前确定。

旧用户可对应新个人家庭，旧孩子与衣服映射到家庭和适配关系。旧日记不能无依据认定为确认穿过，保留来源标识。旧 URL 能否访问及 COS 资产归属需清单核对。

现有 Ark 识别、gptsapi 推荐、COS、天气供应商作为适配候选沿用；本轮不安装依赖、不验证最新 SDK、不调用真实模型。展开适配实施任务时查询官方文档并锁定版本，密钥仅本地或部署配置加载。

所有模型日志记录 request_id、任务、供应商、模型、耗时、状态及截断脱敏摘要；密钥、签名参数、完整图片和儿童个人资料不进普通日志。精细调试按开发配置显式开启。

## 9. 规划自检

产品需求覆盖：家庭档案→A；集中录入/衣橱→B；今天明天/备用/审美/选择→C；反馈/日历→D。图片选填、身体未知由 A 验收；不补记仍有用由 C/D 验收；AI 试穿没有混入首版任务。

本提案尚未执行代码修改或数据库迁移。优先展开 A 的完整实施计划，后续各阶段基于已稳定的领域契约继续细化，避免一次生成跨全部子系统的不可审阅计划。
